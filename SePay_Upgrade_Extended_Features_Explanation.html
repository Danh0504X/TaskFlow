🗄️ CHƯƠNG I: BẢN ĐỒ TƯƠNG TÁC 4 COLLECTION MONGODB ATLAS
Database Core
I. CẤU TRÚC 4 COLLECTION TRONG DATABASE `test`

Mọi tính năng thanh toán, cấp/gỡ PRO và lưu vết lịch sử trong hệ thống TaskFlow được vận hành dựa trên 4 Collection MongoDB Atlas được liên kết chặt chẽ với nhau:

Tên Collection Model Mongoose Mục Đích Sử Dụng & Vai Trò Trong Hệ Thống Hành Vi CRUD Chính
`users` `User.js` Chứa thông tin tài khoản người dùng, vai trò (`role`: admin/user), trạng thái gói (`plan`: FREE/PRO) và Ngày hết hạn gói (`currentPlanExpiresAt`). • Read: Đăng nhập, kiểm tra hạn PRO.
• Update: Cập nhật `plan = PRO` & `currentPlanExpiresAt` khi khớp đơn hoặc Admin cấp thủ công. Đưa về `FREE` & `null` khi gỡ PRO.
`upgradetransactions` `UpgradeTransaction.js` Quản lý tất cả các đơn hàng nạp PRO (bao gồm đơn tự động `TFxxxxxx` và đơn xử lý thủ công `MANUAL_xxxxxx`). • Create: Tạo đơn PENDING khi bấm Nâng cấp PRO, hoặc tạo đơn UNMATCHED khi khách gõ sai mã.
• Update: Chuyển `status = PAID` & `resolutionStatus = AUTO` khi nhận Webhook khớp.
`webhooklogs` `WebhookLog.js` Nhật ký nhận dữ liệu thô (raw payload) từ ngân hàng gửi qua SePay Webhook. Đóng vai trò làm bằng chứng đối soát tài chính nguyên văn và chống trùng Webhook. • Create: Lưu ngay 1 bản ghi khi SePay đẩy tín hiệu Webhook tới server.
• Read: Admin hiển thị bảng Nhật ký Webhook SePay (`/admin/payments`).
`auditlogs` `AuditLog.js` Nhật ký Hệ thống (Audit Log) lưu trữ vĩnh viễn các thao tác quan trọng của Admin (Cấp PRO, Gỡ PRO, Khoá/Mở khoá tài khoản). • Create: Backend tự động ghi log khi Admin thực hiện Cấp/Gỡ PRO hoặc sửa user.
• Read: Hiển thị trang Nhật ký Hệ thống (`/admin/audit`), không bị mất khi F5.

🛡️ CHƯƠNG III: CƠ CHẾ CHỐNG TRÙNG WEBHOOK (IDEMPOTENCY CONTROL)
Security & Integrity
I. VẤN ĐỀ NGUY HẠI KHI KHÔNG CÓ IDEMPOTENCY
Các cổng thanh toán như SePay sử dụng cơ chế Retry Policy (Thử lại khi có sự cố mạng). Nếu đường truyền từ SePay sang server bị trễ vài giây, SePay sẽ tự động bắn lại request Webhook thứ 2 hoặc thứ 3 cho cùng 1 giao dịch ngân hàng:
  • ❌ Tài khoản bị cộng dồn hạn lặp lại: Khách trả 2.000đ cho 30 ngày PRO, nhưng bị cộng thành 60 ngày hoặc 90 ngày.
  • ❌ Bảng Log bị ghi lặp rác: Trang Admin hiển thị 2 đến 3 dòng log giống hệt nhau cho cùng 1 mã giao dịch `FT26223105620067`.
II. GIẢI PHÁP CHỐNG LẶP TRIỆT ĐỂ BẰNG `bankReferenceCode`

Backend sử dụng trường bankReferenceCode (Mã tham chiếu giao dịch ngân hàng) trong Collection webhooklogs làm khóa kiểm tra duy nhất (Unique Idempotency Key): 

// Mã nguồn trong paymentService.js (handleSePayWebhook):
async handleSePayWebhook(webhookData, authHeader = '') {
  const { referenceCode } = webhookData

  // 1. Kiểm tra Chống lặp Webhook (Idempotency Check)
  if (referenceCode) {
    const existingLog = await WebhookLog.findOne({ bankReferenceCode: referenceCode })
    if (existingLog) {
      console.log(`⚠️ Webhook [${referenceCode}] đã được xử lý trước đó. Bỏ qua ghi lặp.`)
      return { success: true, message: 'Giao dịch đã được xử lý trước đó (Bỏ qua ghi trùng)' }
    }
  }

  // 2. Tiếp tục luồng xử lý khớp đơn và nâng PRO...
}
❓ HĐPB: Tại sao dùng `bankReferenceCode` làm Idempotency Key lại an toàn tuyệt đối?
👉 Trả lời: Mỗi giao dịch qua Internet Banking của ngân hàng Việt Nam (MBBank, Vietcombank, Techcombank...) luôn sinh ra duy nhất 1 Mã tham chiếu (Mã FT/Reference Code) không bao giờ trùng lặp. Việc dùng mã này làm khóa chặn ở ngay dòng đầu tiên của Webhook Service đảm bảo 100% request trùng lặp từ SePay sẽ bị từ chối an toàn.
📜 CHƯƠNG IV: HỆ THỐNG NHẬT KÝ HỆ THỐNG (AUDIT LOG) LƯU MONGODB ATLAS
Persistence Architecture
I. GIẢI QUYẾT TRIỆT ĐỂ VẤN ĐỀ MẤT DỮ LIỆU KHI F5
Trước đây, danh sách Audit Log được lưu tạm trong bộ nhớ RAM (React Query State) của trình duyệt. Do đó, khi Admin bấm F5 (Reload), toàn bộ nhật ký cấp/gỡ PRO sẽ bị xóa sạch.

Giải pháp nâng cấp Full-Stack:
  • Tạo Mongoose Model AuditLog.js đại diện cho collection auditlogs trên MongoDB Atlas.
  • Tạo Router /api/admin/audit và Controller adminAuditController.js hỗ trợ phân trang, lọc theo loại hành động, email admin và khoảng thời gian.
  • Đơn nguồn sự thật (Single Source of Truth): Loại bỏ toàn bộ các lệnh `appendAudit.mutate()` ở Client. Mọi bản ghi Audit Log đều được tạo tự động từ Backend Service khi thao tác hoàn tất thành công, chặn đứng lỗi ghi lặp 2 dòng log cho 1 cập nhật.
II. CHI TIẾT MÔ HÌNH MONGOOSE AUDITLOG MODEL
import mongoose from 'mongoose'

const auditLogSchema = new mongoose.Schema(
  {
    adminName: { type: String, required: true },
    adminEmail: { type: String, required: true },
    action: {
      type: String,
      required: true,
      enum: ['USER_ROLE_CHANGE', 'USER_STATUS_CHANGE', 'USER_PRO_GRANT', 'USER_PRO_REVOKE', 'USER_LOCK', 'USER_UNLOCK', 'USER_DELETE'],
    },
    targetLabel: { type: String, required: true }, // Email người dùng bị tác động 
    detail: { type: String, default: '' },        // Lý do chi tiết
  },
  { timestamps: true }
)

export default mongoose.model('AuditLog', auditLogSchema)

PAY-09: Admin Cấp Hoặc Gỡ Gói PRO Thủ Công (Logic Số Âm & Gỡ Tức Thì)
Admin Feature
I. ĐẶC TẢ NGHIỆP VỤ NÂNG CAO
  • Trừ ngày PRO (nhập số âm vd: `-10`): Trừ bớt 10 ngày từ thời hạn hiện tại. Nếu sau khi trừ mà hết hạn ➔ Tự động đưa về `FREE`.
